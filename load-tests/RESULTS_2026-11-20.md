# Dashboard / Supabase load and RLS test — 2026-11-20

## Scope

This test used the deployed Supabase project behind the dashboard. It did **not** test n8n, Telegram, Gemini, or full browser paint time. It created isolated tenants whose names began with `__LOADTEST_`, created synthetic users/data, exercised the same Supabase requests used by the dashboard, and removed every temporary tenant, row, and Auth user afterwards.

No credential, access token, password, or customer data is recorded in this report.

## Baseline smoke test

- Founder password authentication: **PASS**
- `is_dashboard_user()` for the supplied founder: **PASS**
- `my_context()` returned an active founder context: **PASS**
- Service-key access needed for safe test setup/cleanup: **PASS**

## Data and tenant isolation test

A 500-rep tenant was provisioned successfully with:

- 500 rep login accounts
- 1,000 clients
- 5,000 visits
- 4,000 confirmed visits and payments
- 500 pending collections
- Stock issues and sessions for every rep

The test also created a second tenant and verified:

| Check | Result |
|---|---|
| Manager A cannot read a rep in tenant B | PASS |
| Manager A cannot update a rep in tenant B | PASS |
| Manager A cannot read a visit in tenant B | PASS |
| A rep reads only their own visits | PASS |
| A rep cannot read a visit in tenant B | PASS |
| Unauthenticated public key cannot read visits | PASS |

All temporary test tenants, rows, and Auth users were successfully deleted after each run. A post-cleanup query found **0** `__LOADTEST_` tenants and **0** test reps remaining.

## Functional scale finding: manager overview is truncated

For the 500-rep dataset, the tenant had **4,000 confirmed visits** in the selected period. The current dashboard overview query returned exactly **1,000** rows because `Overview.js` applies `.limit(1000)` before calculating totals.

**Result: FAIL for accurate large-tenant reporting.** The manager overview would undercount sales, rep rankings, and the 14-day chart after the tenant exceeds 1,000 matching visits.

## Authentication burst test: 500 simultaneous password logins

| Metric | Result |
|---|---:|
| Requests | 500 |
| Successful | 31 |
| HTTP 429 rate-limited | 469 |
| Successful-login P95 observed in mixed run | 2.1 s |

This is a Supabase Auth anti-abuse/rate-limit result. It does not mean 500 already-authenticated users cannot use the product; however, the project cannot currently support a single-source burst of 500 fresh password logins. Real users will be distributed across networks, but a launch/day-start burst must still be planned and tested after checking the project Auth rate-limit settings.

## Controlled RepToday API load tests

Each virtual rep executed the same request pattern as the current rep dashboard:

1. `is_dashboard_user()` RPC
2. Read own rep identity
3. Four parallel reads: visits, payments, collections, `rep_stock`

### 10 concurrent reps

All requests succeeded. P95 per request family was roughly **0.7–1.4 seconds**.

### 50 concurrent reps

All requests succeeded, but response times were already high:

| Request | P95 |
|---|---:|
| `is_dashboard_user()` | 4.3 s |
| Own rep lookup | 3.0 s |
| Today visits | 3.6 s |
| Payments | 3.3 s |
| Collections | 3.2 s |
| Stock | 4.3 s |

The complete 50-rep boot wave finished in 6.69 seconds.

### 100 concurrent reps

All requests returned HTTP 200, but latency is not acceptable for a 500-rep target:

| Request | P95 |
|---|---:|
| `is_dashboard_user()` | 6.7 s |
| Own rep lookup | 10.3 s |
| Today visits | 8.7 s |
| Payments | 10.4 s |
| Collections | 8.7 s |
| Stock | 10.8 s |

The complete 100-rep boot wave took 15.52 seconds. At 500 concurrent fresh dashboard loads the expected behavior is worse, not better.

## Verdict

- **Security isolation baseline:** passed in the tenant/RLS scenarios tested.
- **500-rep data setup:** passed.
- **500 simultaneous fresh password logins:** failed due to Auth rate limiting.
- **100 simultaneous RepToday loads:** no HTTP failures, but P95 latency reached 6.7–10.8 seconds.
- **500-rep manager reporting:** currently inaccurate once data exceeds the 1,000-row frontend limit.

The deployed system is suitable for small controlled pilots. It is **not ready to promise smooth, accurate operation for a tenant with 500 active reps** without the performance changes below.

## Required changes before a 500-rep rollout

1. Replace manager-side raw-data aggregation with SQL RPCs/views, for example `dashboard_overview(date_from, date_to)`. Return aggregates rather than downloading up to 1,000 visits.
2. Replace RepToday's six startup calls with one or two RPCs that return the rep context, KPIs, pending collections, and stock summary.
3. Add pagination/server-side filtering for visits, clients, stock issues, and invoice history.
4. Add composite indexes that match tenant-scoped query patterns, especially:
   - `(tenant_id, status, created_at desc)` on `visits`
   - `(tenant_id, rep_id, created_at desc)` on `visits`
   - `(tenant_id, created_at desc)` on `payments`
   - `(tenant_id, status, due_at)` on `collections`
   - `(tenant_id, rep_id, created_at desc)` on `stock_issues`
5. Review Supabase project compute plan, region, connection pool, and Auth rate limits. Retest from a production-like region.
6. Keep user sessions persistent, add client retry/backoff for transient errors, and avoid a forced simultaneous password-login event.
7. Before bot load testing, run n8n in queue mode with monitoring, retries, and a verified Gemini quota.
